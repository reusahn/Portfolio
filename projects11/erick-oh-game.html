01 / PROCEDURAL SURFACE

Procedural Cloud Surface Shader

The cloud was an opaque mesh, not a volumetric raymarched cloud. The goal was to make the surface feel alive and wind-driven while keeping the object responsive to player input.

PROCEDURAL CLOUD — RUNTIME RESULTVIMEO · REAL-TIME CLOUD SURFACE
UNITY DEVELOPMENT VIEWVIMEO · RUNTIME / SHADER TEST
Task 01A / Surface Motion

Creating cloud-like motion without moving the mesh as a rigid object

The visual requirement was internal surface motion rather than simply translating the whole cloud. I built a custom HLSL surface shader using Perlin-noise-driven vertex displacement so the cloud could deform continuously while the GameObject itself remained in place.

Opaque mesh surface in Unity URP.

Perlin noise drives spatial variation in the deformation.

Vertex displacement occurs in the shader.

Fresnel-based lighting helps reinforce the cloud silhouette and edge response.

Result

A lightweight real-time cloud surface with visible internal motion rather than a static mesh or rigid transform animation.

Task 01B / Runtime Control

Connecting directional player input to shader behavior

The player needed to influence the direction of the cloud’s internal motion. I kept input and gameplay logic in C#, then passed directional values into the material as shader parameters.

02 C# Direction Vector
03 Material Vector / Float Parameters
04 HLSL Noise Flow
05 Directional Surface Motion
Control Model

The player's input changes the shader's internal noise-flow direction; the cloud GameObject itself is not simply translated through the scene.

CHAPTER OUTCOME

The cloud shader demonstrates a direct Technical Art handoff between interaction logic and graphics: C# interprets user input, while HLSL turns those parameters into art-directed surface motion.

02 / RAYMARCHED LIQUID

Player-Controlled Raymarched Metaball Liquid

The liquid needed to behave as multiple gameplay objects while visually reading as one continuous mass. I separated gameplay representation from rendering representation instead of forcing both responsibilities into the same structure.

Task 02A / Gameplay Representation

Keeping droplets as separate controllable objects

Each droplet remained its own GameObject with collision behavior. That made it possible to detect contact, move objects through C#, and maintain gameplay logic independently of how the final liquid was rendered.

Similarly sized droplet GameObjects.

Collider-based contact / proximity recognition in C#.

Player-driven transform / velocity behavior handled in C#.

Collected droplets remain separate underlying objects after joining the group.

Task 02B / Group Behavior

Constraining collected droplets so the cluster moves as one system

After droplets were collected, one droplet acted as the leader / parent reference and the remaining droplets followed the group. C# positional correction prevented individual droplets from drifting too far apart.

Task 02C / Visual Representation

Using a raymarched metaball field to visually fuse separate objects

The gameplay objects did not need to merge into one mesh. A custom HLSL raymarched metaball field provided the continuous liquid appearance while C# preserved the individual droplet objects underneath.

Custom HLSL raymarching.

Metaball-style field visually fuses nearby droplets.

C# owns movement, collision, and grouping; HLSL owns the continuous liquid appearance.

Multiple gameplay droplets read as a single player-controlled liquid mass.

CHAPTER OUTCOME

The metaball system shows the clearest separation between gameplay logic and rendering in this project: physically separate objects remain easy to control and collide, while the shader provides the illusion of one continuous fluid body.

03 / FIXED TOPOLOGY

Vertex-Preserving Cloud Growth

A cloud needed to grow from a small form into a larger one, but topology-changing simulation would break the vertex correspondence required for blendshape animation. I chose a deterministic fixed-topology workflow instead.

FOUR MATCHING-TOPOLOGY STATES
MAYA GROWTH TARGET — MULTI-VIEW VALIDATION
Task 03A / Topology Constraint

Designing around blendshape correspondence

A simulated growth process could have produced the desired visual change, but changing topology would make the resulting states unusable as blendshape targets. The technical constraint therefore became part of the art-direction strategy.

Small → large cloud growth.

Blendshape targets require consistent vertex count and ordering.

Do not use topology-changing simulation for the final playback system.

Author a controlled set of fixed-topology growth states in Maya.

Task 03B / Maya Authoring

Building four growth states while preserving vertex identity

I created exactly four cloud growth states in Maya. Each state preserved the same vertex count and ordering, allowing the shapes to function as reliable blendshape targets.

Task 03C / Unity Playback

Turning DCC-authored states into an art-directable real-time animation

The four Maya states were connected as blendshape targets and animated in Unity using Timeline / Animation keyframes. The growth was therefore deterministic and easy to art-direct rather than being generated procedurally at runtime.

Four Maya growth states.

Blendshape weights interpolate between the fixed-topology states.

Weights keyframed through Unity Timeline / Animation.

Stable, repeatable cloud growth without topology changes.

Production Value

The solution traded simulation complexity for deterministic control, which made the growth easier to direct, reproduce, and integrate into the real-time sequence.

CHAPTER OUTCOME

This system demonstrates a different Technical Art decision from the shader work: instead of solving the problem entirely in code, I preserved a DCC-authored deformation workflow because it provided the predictability and control the shot needed.
