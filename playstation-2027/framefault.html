Flagship research proposal M1 / Multimodal anomaly detection

FrameFault.
When play breaks, find the moment.

Build an instrumented game benchmark and a trainable multimodal anomaly detector. The research question is not whether unusual video looks unusual, but whether synchronized actions, visual motion, engine signals, and game context can locate genuine gameplay faults while ignoring surprising yet valid play.

Research project specification · Not a completed ML experiment
Modality: video + controller + engine telemetry; audio optionalFramework: Unity / Python / PyTorchReview output: reproducible models, benchmark, ablations, failure cases

01 / Research hypothesis

Detect a failure, not merely a rare event.

Proposed hypothesis H1: synchronized video and player-input features, conditioned on discrete game-state context, will reduce false alarms on intentional mechanics compared with video-only or input-only detectors at comparable event-level recall. This is a hypothesis to test, not an established result.

H2: explicitly separating event onset localization from per-frame classification will improve reviewer usefulness even when headline frame metrics look similar.

Research value: a QA analyst needs the probable onset, reproducible context, event type, and a short evidence clip—not a timeline flooded with unexplained alarms.

What a reviewer can inspect

  • Playable Unity capture scene with bug injection menu
  • Synchronized recording of video, actions and states
  • Event label ontology with ambiguity policy
  • Train/validation/test provenance and leakage checks
  • Rule-based and learned baseline implementations
  • Model ablations, calibrated thresholds and held-out error gallery
  • One-button analysis of a withheld gameplay clip

02 / Instrumented dataset design

Construct cases with known causes and hard negatives.

Begin with a small original Unity game level that you own and can modify: movement, climbing or jumping, one combat interaction, scripted animation and a UI/pause state. A configurable fault injector creates reproducible problems. Log every intervention with a shared monotonic game clock; record screen video and input at documented rates. Preserve the unaffected baseline replay for each trial.

Fault classInjected fault and ground-truth onsetVisually similar valid counterexample
Movement stallPlayer input accepted but velocity unexpectedly clamped during control-active stateIntended idle, start menu, cutscene lock
Illegal teleportPosition jumps without corresponding ability/portal/respawn eventLegal dash, teleport ability, respawn transition
Collision violationCharacter penetrates a tagged solid collider or passes a prohibited boundaryAuthorized traversal animation or destructible wall
Input-response desyncConfigured input delay or wrong action mapping when control should be activeIntentional buffering, hit-stop, stun, charge-up
Animation-state mismatchMovement state and animation state deliberately desynchronizedBlend transitions and authored animation cancel
Progression softlockPrerequisite completed but interactive objective cannot progressIntentional blocked door or unfinished objective

Capture schema (planned)

  • run_id, session_id, seed, scenario_id
  • t_monotonic_ms and video-frame presentation timestamp
  • Controller action vector, held/tapped state, deadzone
  • Player pose, velocity, collider tags, ability, menu/control state
  • Event start/end, category, injector config and source
  • Audio events only if synchronization quality permits

Minimum useful dataset target

  • Target 6 fault types + at least 6 normal hard-negative contexts
  • Multiple random seeds, trajectories, speeds and camera viewpoints
  • Several distinct arena/background variants with changes recorded
  • Define annotation exclusion zones around ambiguous transitions
  • Group clips by entire run; avoid adjacent windows across splits
  • A truly unseen scenario family is held out to test generalization

These are design requirements, not completed dataset counts. The actual sample size and reliability report must accompany evaluation.

03 / Model and baseline ladder

Beat interpretable baselines before claiming multimodal intelligence.

ModelInput / architectureWhat it tests
B0 · heuristicResidual change-point detector and explicit rule checks on action/velocity/stateStrong, fast and explainable classical baseline
B1 · video onlyFrozen pretrained video/frame embeddings + shallow temporal headHow much fault evidence is visible without telemetry?
B2 · action/state onlyNormalize action and state traces; temporal CNN or compact GRU classifierAre bugs detectable from instrumented game logic alone?
B3 · late fusionTime-aligned B1/B2 representations with a gated fusion prediction headDo visual and state signals add complementary evidence?
B4 · optional VLMFrozen vision-language model prompting or feature extraction on selected clipsCan language-based scene context explain errors? Avoid unnecessary expensive training.

Recommended PyTorch structure

  • capture/ — Unity instrumentation and sync specification
  • datasets/ — session-grouped temporal windows
  • models/visual.py — frozen video representation
  • models/action.py — controller/telemetry sequence encoder
  • models/fusion.py — learned sequence fusion
  • train.py, evaluate.py, calibrate.py
  • reports/failure_gallery/ — annotated clips + traces

Non-negotiable experiment controls

  • Predefine holdout split and event tolerance before tuning.
  • Never use bug-injector ID as an input feature.
  • Mask debug overlays if camera pixels include labels.
  • Freeze source encoder where sample size is limited; compare compute fairly.
  • Separate train and held-out level/layout/camera conditions.
  • Track seed, config, weights, hardware and runtime.
  • Compare inference latency and false alarms at matched recall.

04 / Evaluation plan · Predeclared targets

Measure events the way QA engineers would use them.

Primary metrics

  • Event recall / precision / macro-F1 using explicit onset-overlap tolerance
  • False alarms per hour across sustained normal play
  • Detection latency from annotated fault onset
  • Generalization gap for unseen fault type or scene configuration
  • Per-class breakdown including ambiguous transitions
  • Confidence calibration on held-out games and settings

Comparisons and ablations

  • Video-only vs action-only vs fused, same evaluation set
  • With / without intentional-ability state information
  • With / without temporal context
  • Normal scene split vs unseen camera/level split
  • Hard-negative stress suite: cutscene, dash, stun, menu, hit-stop
  • Grouped bootstrap by independent sessions, not adjacent windows
Release gateRequired evidence (not a claimed result)
ReproductionFresh environment can reconstruct the published split and rerun B0/B1/B2/B3 evaluation from a frozen manifest.
Useful detectionShow verified event-level metrics and false alarms/hour; document at least 10 qualitative true-positive and failure examples when dataset size allows.
Multimodal contributionPrespecified fusion-vs-single-modality comparison with confidence interval and clearly interpreted null or negative result.
Research integrityNo leaked run IDs, no test-set threshold tuning, ground-truth ambiguity documented, negative controls visible.
Deployment realismCapture-to-score latency, device specs, compute budget and pipeline failure handling documented.

Publication-quality aim: a controlled multimodal benchmark with a reproducible hard-negative suite and insight into where video and action signals help each other. Publishing a paper is a goal only, not an achievement being claimed.

05 / Milestone roadmap

Build in dependency order, not appearance order.

Gate 1 · Capture

Playable game, fault injector, paired clean/fault runs, timestamp alignment and a small labeled manifest. Verify data synchronization.

Gate 2 · Baselines

Implement frame/event ground truth, heuristic detector, visual encoder and action encoder. Freeze split and record robust negatives.

Gate 3 · Research

Train fusion model; run ablations, held-out scenario evaluation, error taxonomy, calibrated threshold and evidence-gallery export.

A / B / C hiring-panel review

Defend the experiment in an interview.

Technical interviewer A

Why is fusion necessary if engine telemetry can expose some injected faults directly? Your study must compare video-only deployment usefulness against oracle telemetry, discuss visibility bias, and distinguish detecting a symptom from reading the injector label.

Research manager C

Could this cut QA triage work? Show false positives/hour at a fixed event-recall target, clipped evidence packets, failure categories and expected reviewer cost—then explain what the model still cannot detect.

Recruiter B — What proves direct contribution?

Present a playable capture build, a public methods README, model code, held-out evaluation figures, one-page methodology abstract, and a demo that labels planned versus measured results.
