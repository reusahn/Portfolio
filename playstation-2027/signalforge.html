Flagship proposal A1 / 3D action-game accessibility

Read the attack. Keep the challenge.

A 3D arena encounter designed to answer a practical accessibility question: can players perceive the same combat information and make meaningful decisions through different sensory and input pathways, without the game silently becoming an entirely different challenge?

01 / Game concept and player loop

A real action challenge with inspectable information.

Build a polished third-person arena: one player character, a single mechanical boss and three short attack patterns. The player reads a telegraph, selects dodge/block/positioning, and recovers. Each attempt produces a replayable event trace.

Core attack vocabulary: radial slam (leave a circle), directional sweep (move toward a safe side), projectile burst (time a dodge). In the baseline these communicate through color, timing, sound and animation. The accessible variations provide equivalent intent-critical information through alternative cues.

This is a game: attack timing, risk, spacing and recovery are preserved across settings unless the player explicitly changes timing assistance.

The 60-second vertical slice

  1. Choose controller / keyboard and presentation preferences.
  2. Learn one attack with optional practice mode.
  3. Survive a three-pattern boss sequence.
  4. Observe precise, understandable success and damage feedback.
  5. Review the event log and retry with a different cue profile.

Do not call a feature accessible solely because it exists. Verify if players can perceive and use it with their own preferred assistive setups.

One semantic cue, several equivalent renderers.

Suggested Unity modules

  • AttackPatternSO — data-driven telegraphs and active frames
  • ThreatEventBus — semantic game event, independent of output
  • VisualCueRenderer / AudioCueRenderer / CaptionRenderer
  • PlayerActionRouter — rebound actions and saved profiles
  • EncounterTelemetry — local anonymized CSV export
  • ReplayController — same attack sequence/seed across comparison runs

Production quality bar

  • Readable animation silhouettes; not a plain capsule-on-grid demo.
  • Consistent cinematic art direction in a compact environment.
  • Effects degrade gracefully in reduced-intensity profile.
  • Pause, reset, tutorial skip and accessible menu navigation.
  • Performance and input latency measured on named test hardware.
  • Video captures showing both baseline and accessible variants.
03 / Inclusive research protocol · Planned

Measure the barrier, not the player's diagnosis.

Primary research question

Does user-selectable, redundant combat feedback improve successful interpretation of telegraphs and recovery from errors without hiding the strategic timing decision?

Study conditions

  1. Current/default presentation of identical seeded encounter.
  2. Player-selected cue configuration, with challenge timing kept equivalent.
  3. Optional timing assistance evaluated separately to prevent confounding.

Use counterbalanced condition order when feasible. Allow self-selected accommodations and participants' own preferred equipment.

Human-centered evaluation

  • Consult people with relevant lived experience early; compensate appropriately where possible.
  • Opt-in, accessible instructions and consent; alternative remote participation pathways.
  • Ask neutral questions; never simulate a disability as the main evidence.
  • Disaggregate findings cautiously; avoid treating a small exploratory sample as population-representative.
  • Document conflicting preferences and where one setting harms another player.

Exit criteria, not fictional results: ship a complete short encounter, offer at least three distinct information channels with no one channel mandatory, supply keyboard/controller rebinding, capture reproducible seeded play logs, and document a review with actual consenting participants or expert consultants. Any percentages are reported only after collecting data and publishing their denominator.

04 / Build schedule

Four delivery gates that can be shown in an interview.

Gate 1 · Mechanics

Playable arena, three telegraphed attacks, dodge/block, damage and restarts. Save seeded game events and replay sequence.

Gate 2 · Accessibility

Separate semantic intent from presentation. Add alternate cues, rebindable controls, settings save, comfort toggles and in-game captions.

Gate 3 · Evidence

Internal technical audit, opt-in feedback sessions, barrier log, before/after changes and reproducible test cases.

Interview readiness / A · B · C

Questions the hiring panel should be able to ask—and see answered.

Technical interviewer A

What stays constant between the default and alternative feedback conditions? Walk through the semantic attack event, a missed cue, the active hitbox and the exact CSV record generated.

Hiring manager C

Which barrier would you fix first, and how would you handle conflicting player preferences? Demonstrate a prioritized issue log, an engineering handoff and a documented retest.

Recruiter B — Can the work be verified quickly?

The first screen must link to a playable build, 60-second feature demonstration, concrete owner contribution and concise participant-tested outcomes—not just attractive concept art.
