Flagship proposal A2 / Existing Unity VR game redesign

Escape Metro.
One puzzle. More than one way in.

Take the existing Unity VR AI-conversation escape game and systematically test whether its central puzzle is playable without one required language, vocal, sensory or motor interaction style. Keep the adversarial dialogue mechanic while changing how players access and understand it.

01 / Existing work → specific accessibility redesign

The puzzle depends on information. The interface should not hide it.

Existing production basis: Escape Metro is a real Unity VR work in which players persuade a protected-information AI to disclose a password to exit. Conversation affects gameplay progression, and a deterministic game state decides when the exit opens.

New research problem: if a player cannot speak, hear, move quickly in VR, remember a transient NPC response or decode conversational failure, can they still solve the same underlying puzzle?

Deliverable: a revised Unity build with a parallel desktop mode and configurable dialogue input/output. The original game is evidence of prior practice; the accessibility redesign and its results are not yet completed.

Existing Escape Metro production evidence ↗

Player-facing journey

  1. Choose VR or desktop / seated experience.
  2. Select dialogue mode: text entry, prompted intent choices, or optional voice input if implemented.
  3. Confront the AI; inspect preserved dialogue history.
  4. Use optional recap to recover goals and conversation state.
  5. Obtain password and open exit; the win condition stays identical.

Prompts are user-editable. A selection-only mode must be designed to preserve strategic choice, not force one answer.

02 / Alternative inputs, comprehension and comfort

Preserve the decision. Remove needless friction.

BarrierPlanned featureExplicit non-goal / trade-off
Speech and languageFully usable keyboard text entry, optional speech pathway, on-screen suggested intents with ability to rephraseNo claim that speech recognition works equally for all accents or communication styles without testing
HearingComplete persistent transcript with speaker labels and system-event captionsCaption timing and screen-reader behavior need implementation review
Memory / cognitionPinned goal, searchable/replayable dialogue, one-click recap of known game factsRecap must not reveal the protected password or alter puzzle outcome
VR motionOptional desktop route, teleport locomotion, snap/smooth turn settings, stable horizon and fade optionsParity of interaction logic, not identical physical embodiment
Motor accessRebindable controls; reduced need for simultaneous presses; target sizes and dwell interactions reviewedAssistive hardware compatibility to be measured, not assumed
LLM unpredictabilityOffline deterministic scenario fixtures, visible waiting/error states, retry controls and explicit safety boundaryNot a proof that all AI systems can be prompted to reveal secrets

Module breakdown (Unity C#)

  • ConversationSession — serializable state, retries, transcript storage
  • InputModeAdapter — text, intent cards, speech extension
  • NPCProvider — deterministic fixture / API implementations
  • AccessibilitySettings — UI, movement, caption preferences
  • GameProgression — authoritative password validation
  • ResearchEventLogger — local participant-consented task events only

Build acceptance tests

  • Win possible in desktop mode without voice.
  • Critical NPC information can be retrieved from persistent text.
  • Same password verification across input modalities.
  • Resuming after a cancelled interaction does not reset dialogue history.
  • Controller and keyboard flow can reach all UI actions.
  • Offline fixture gives identical NPC responses for equivalent test condition and seed.
03 / Research protocol · Planned

Can the same puzzle remain solvable through alternative pathways?

Comparison design

Construct 3–4 representative puzzle stages, each with a fixed offline NPC response fixture. Compare the existing interaction pathway with selectable alternative pathways; preserve level, password and informational content. Within-person contrasts should counterbalance order when practical; participants choose safe comfortable modality.

Include a separate exploratory live-model condition, not pooled uncritically with deterministic trials because response difficulty varies by prompt and model version.

What to observe

  • Completion and task abandonment with session context
  • Repeated instructions, lost conversational state, accidental skips
  • Time and number of actions to recover after an unclear NPC reply
  • Discoverability and use of alternative controls
  • Consent-based interviews about agency, comfort and comprehension
  • Screen-reader/keyboard/device compatibility audit

Responsible evaluation: do not request sensitive diagnoses as proof of eligibility to playtest. Invite accessibility feedback from people with relevant experiences, ensure reasonable compensation and informed consent, collect minimal personal data, and report small samples transparently. Expert review and disability-led playtesting are different forms of evidence and should be labeled separately.

04 / Before-and-after review

Three revisions worth demonstrating on screen.

1 · Conversation recovery

Show a missed NPC instruction; recover it through history without restarting the challenge. Capture the step-by-step screen flow.

2 · Input parity

Complete the same guarded-password scene through keyboard text and selected intent. Audit mechanical differences and unresolved trade-offs.

3 · Comfort choice

Move through the same subway objective in seated VR and desktop contexts. Document locomotion options and which spatial cues must be preserved.
