Signal Path

Find a route around the barriers. Move with arrow keys, WASD, or on-screen buttons. State changes are always expressed in text, not only in color or motion. Try the display preferences and request a hint if needed.

Display preferences

Preferences affect this demonstration only. They are optional and do not change puzzle difficulty. System reduced-motion preference is also respected by the stylesheet.

Task

Start on the left. Reach the goal on the right. Wall tiles cannot be crossed. Moves are turn-based; there is no timer.

Keyboard: ← ↑ ↓ → or W A S D. H for hint. R to restart. Keyboard shortcuts do not intercept typing in form controls.

Play / Step-by-step wayfinding

Navigate to the goal.

You are at column 1, row 2. Find the goal at column 5, row 2.

Board labels: YOU is your current position; GOAL is your destination; WALL cannot be entered. Each tile has a spoken label.

Session information (local only)

0 moves · 0 blocked attempts · 0 hints

Nothing is uploaded or logged to a server. These counters are descriptive affordances, not participant data or accessibility outcomes.

Design decisions / Prototype rationale

Why the interface behaves this way.

This sample isolates a few testable interaction choices. No automated checklist can establish that a game is accessible to everyone.

Equivalent input choices

Arrow keys, WASD and on-screen buttons operate the same state transition. No path requires pointer precision, a microphone, or timed input.

Redundant state cues

Tiles use explicit words and visible boundaries, with a live text description. The goal and obstruction remain identifiable when color differs or cannot be perceived.

Recovery and cognitive support

Blocked moves do not end the task; the reason is announced, and the hint uses a shortest-path search to provide the next permitted move. Restart is always available.

Proposed inclusive research session

  1. Ask participant about preferred interface and input method without assuming needs.
  2. Observe route discovery with no explanation; document unclear instructions.
  3. Offer hint and preference controls; observe whether the alternatives remain understandable.
  4. Conduct a neutral interview about clarity, control, effort, and points of friction.
  5. Prioritize findings with UX/design/engineering and implement a revision.

This is a plan, not a session that has already been conducted.

Useful measures—still uncollected

CompletionTask completion by participant-preferred input route
RepairBlocked-action frequency, recovery steps, and hint use
ComprehensionCorrect understanding of wall, player, and goal state
PreferenceComfort and agency reported directly by participants

Limitations: this short web sample does not test VR comfort, screen reader compatibility across device/browser combinations, controller remapping, motor fatigue, or full game accessibility. A thorough evaluation needs opt-in player participation, platform testing, and expert guidance.
