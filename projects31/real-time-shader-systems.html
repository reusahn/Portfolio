Runtime graphics built for iteration

The project needed expressive visual behavior that could react to runtime state while remaining controllable enough for production iteration.

Implementation

  • Built an opaque mesh-cloud system using custom HLSL Perlin-based vertex displacement and Fresnel-based presentation.
  • Connected C# input to internal shader noise-flow direction rather than merely translating the GameObject.
  • Prototyped a raymarched metaball field while keeping visual-field rendering separate from gameplay collision / proximity logic.
  • Built a deterministic four-state transformation system using fixed-topology Maya blendshape targets and Unity Timeline / Animation keyframes.
Runtime Input ↓ C# State / Parameters ↓ HLSL Shader Behavior ↓ GPU Visual Response Visual rendering ≠ Gameplay collision / proximity logic

Why this is pipeline evidence

The hard part was not writing one shader. It was deciding which layer should own each behavior, keeping the visual system controllable by production, and debugging whether a failure belonged to shader math, runtime state, animation, or interaction logic.
