01 / PROBLEM & OWNERSHIP

A design problem translated into a runtime system.

The distinction between creative objective and technical contribution is central to this case.

Design / production challenge

A garment and rig that appear correct in DCC or an editor may break under different poses, scale or device conditions. The runtime needed responsive controls and cloth that continued to behave across animation transitions.

My technical contribution

I prepared and retargeted humanoid animation, cleaned skin weights, configured Unity Cloth and collisions, implemented animation and camera controls, and built an Android APK for direct device validation.

02 / IMPLEMENTATION

How the feature works.

Concrete subsystems and boundaries, not only a list of software tools.

Interactive animation

Selectable ARGUE, DANCE, FIGHT, POINT and TALK states are available in the runtime.

Cloth simulation

Cape cloth uses Unity Cloth constraints and colliders rather than relying only on baked animation.

Look-at and framing

Camera control and look-at behavior make character movement inspectable from different viewpoints.

On-device validation

Android build verifies interaction, simulation and character presentation beyond the Unity editor.

Retargeted animation→Unity Animator→Cloth + collision→Touch camera / UI→Android build
03 / TECHNICAL DESIGN

Decisions that make iteration possible.

Each technical decision supports clarity, performance, or cross-disciplinary change.

Why test multiple clips?

Different poses expose weighting and collision problems that a single idle pose will miss.

Why runtime cloth?

A live solver responds across animations and user-controlled pose changes.

Why Android?

Target-device validation can expose input, performance and rendering issues hidden by the editor.
