TECHNICAL DESIGN FRAMEWORK

I design the loop before I decorate the scene.

The recurring question across my interactive work is: what does the player do, what changes in response, how clearly is that change communicated, and what does the next beat ask from the player? The implementation can be C#, animation, shader state, dialogue, or spatial staging — but the design logic has to remain readable.

01 / GAMEPLAY SCENARIO

Goal → obstacle → action → resolution.

Prototype the smallest playable loop, test whether the player understands the goal, then add complexity only when the core interaction reads.

Proof: Escape Metro · Erick Oh Game
02 / INTERACTIVE OBJECT

Input should produce a legible state change.

Player action is connected to a visible or behavioral response so the object communicates what changed and what remains possible.

Proof: Erick Oh Game · Be NARCI
03 / NARRATIVE SEQUENCE

Emotion is shaped by timing, space, and agency.

Blocking, camera, encounter order, dialogue, and player perspective can carry narrative information without separating story from interaction.

Proof: NARCI · Jooan · Mythomania
04 / CHARACTER BEHAVIOR

Animation has to survive implementation.

Character motion, facial performance, retargeting, and state changes are evaluated in the final engine context rather than as isolated DCC output.

Proof: Shininho/Jooan · Gang Se-hwang
05 / ITERATION

Build → observe → diagnose → tune.

I am comfortable crossing art and engineering boundaries when a prototype fails — changing code, timing, animation, camera, materials, or the interaction itself.

Proof: all selected projects
