01 / PROBLEM & OWNERSHIP

A design problem translated into a runtime system.

The distinction between creative objective and technical contribution is central to this case.

Design / production challenge

A distinctive material language is only useful in a game when it can react immediately, repeat consistently and remain easy to change during development. A purely cinematic shader would not satisfy player control or game-logic requirements.

My technical contribution

I built shader-driven behavior connected to C# runtime controls, combined proximity-aware interaction with a separate raymarched representation, and integrated four fixed-topology transformation states. The aim was a controllable system rather than a pre-rendered effect.

02 / IMPLEMENTATION

How the feature works.

Concrete subsystems and boundaries, not only a list of software tools.

Directional response

Player input updates the internal noise-flow direction of a Perlin-style vertex-deformation shader; the object does not simply translate.

Visual/collision separation

Raymarched metaball visuals and collision/proximity detection are separate layers, allowing art tuning without redefining interaction geometry.

Repeatable state transitions

Four Maya-authored targets with matching topology form predictable transitions that can be animated and revisited in Unity.

Art-directable iteration

Separate parameters for deformation, Fresnel presentation and state changes support visual iteration while the core input remains intact.

Player input→C# state / parameters→HLSL deformation→GPU response
03 / TECHNICAL DESIGN

Decisions that make iteration possible.

Each technical decision supports clarity, performance, or cross-disciplinary change.

What owns movement?

C# owns input and state; HLSL owns how the state looks. This avoids hiding gameplay behavior inside a shader.

How are contacts detected?

Collision and proximity are evaluated independently of a raymarched field, providing stable control over interaction.

How are transitions tested?

Known blendshape targets and named states allow comparison between transitions without rebuilding source meshes.
