Problem & individual contribution

Make process boundaries observable.

A visitor’s portrait had to move through capture, visual processing, storage, and display without a manual handoff. The installation also had to coordinate multiple participants rather than treating every portrait as an isolated offline result.

I implemented: Unity integration, Python/OpenCV coordination, networked portrait output, and exhibition-side execution.

I integrated the Unity application with Python/OpenCV processing and networked output. My project record describes up to four concurrent participants using TCP/UDP. The public technical archive specifically documents TCP delivery of completed portraits to a separate display. The packet-level role of UDP still needs its own code or runtime capture.

Implementation decisions

Why the system is structured this way.

01

Separate creation from presentation

Capture and image processing produce a completed portrait. The display wall consumes that output as a separate responsibility. This boundary is documented by the existing archive.

02

State the concurrency accurately

The project supports a multi-participant exhibition format with a reported maximum of four. That describes this installation. It does not establish matchmaking, replicated physics, or commercial online game operations.

03

Expose a transport boundary in public code

The new example uses a length-prefixed PNG frame, a bounded queue, and main-thread image decoding. It illustrates one useful boundary without presenting a reconstruction of the original client code.

Debugging record

Earlier portfolio notes mention audio buffering and playback interruptions. They do not contain a reproducible incident log. That remains an evidence task. The new transport example includes partial-frame and disconnect scenarios so a reviewer can examine a concrete failure path now.

Public implementation example

A boundary you can inspect.

Implemented in this update / source only

This independent receiver handles one active sender at a time. It reads the complete frame on a worker, bounds pending packets, then decodes and updates a texture on Unity’s main thread. The Python sender can deliberately split a frame or disconnect early. It does not include the production vision model, four-user coordination, UDP path, archive, or delivery acknowledgement.

Validation: These files were authored for this portfolio. They have not been compiled or executed in Unity. They are independent examples, not original client source.
