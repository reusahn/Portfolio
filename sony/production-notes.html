Capture-to-engine
production notes.

A practical reference distilled from the Shininho, Row, Gang Se-hwang, and When It Seen workflows.

Authored for this portfolio. This is a retrospective process summary, rather than a contemporaneous production log or a claim of operating every capture system described.

1. Define the source and the destination.

Before capture or conversion, agree on the final representation: an editable character rig, facial animation, engine-ready performance, or deforming geometry for another department. Separate the identity source from performance and reference recordings.

StageRecord / agreeReview before proceeding
Source intakeSubject / take identifiers, capture method, reference footage, intended character system.Can the source be opened? Is identity capture distinct from performance? Are teeth, head turns, or other required references available?
Performance capturePerformer setup, calibration, take purpose, sync reference, visible tracking failures.Is tracking usable during difficult movement? Does the take need to be repeated while the performer is still available?
Character buildSource mesh, target topology, texture transfer, rig / facial-channel convention.Does likeness survive the rebuild? Do eye placement, skin detail, and expression deformation work in engine?
Animation integrationBody / face take pairing, timing alignment, cleanup decisions, baked output.Are contact and timing coherent? Are tracking gaps repaired? Does the final rig retain the intended performance?
HandoffDestination DCC / engine, required representation, frame range, frame rate, scale, included geometry.Open the exported asset in its destination and check timing, deformation, materials, and playback.

2. Record the failure and the decision.

Describe the observed defect before selecting a tool. Preserve the source, identify the affected range or character, document the chosen correction, and compare the corrected result in the target context.

3. Make ownership explicit at the handoff.

Shininho’s original volumetric scan came from an external studio. Row’s participant footage was recorded by the artist using my requirements. When It Seen’s Houdini simulation belonged to the downstream team. Recording these boundaries helps collaborators know which assets, decisions, and follow-up questions belong to each person.

4. A reusable handoff record.

The following is a proposed checklist for future documentation. It is not presented as a completed historical project record.

  • Project / character / take identifier and source-file version.
  • Capture setup, operator, calibration, synchronization reference, and known limitations.
  • Observed issue, affected frames, correction, and comparison reference.
  • Export representation, frame range, frame rate, units, axis convention, and geometry included.
  • Destination application / engine and the result of reopening the exported asset.
  • Remaining known issues and the person responsible for the next stage.

Example naming pattern for future use: project_subject_take_stage_version. Use the receiving team’s existing convention when one is defined.
