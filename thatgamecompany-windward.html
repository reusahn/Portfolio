WORKING TITLE · UNITY C# · TWO-PLAYER ONLINE CO-OP

Windward.

Two players, two complementary forces, one shared goal. An online co-op prototype in which one player lifts a drifting seed while the other steers it through a sequence of floating environments.

01 / PLAYER EXPERIENCE

A small mechanic with genuine interdependence.

The game is designed around cooperation rather than two players doing the same thing. Neither can complete a level alone: vertical lift and horizontal steering must be combined to move a fragile seed past obstacles into a safe landing zone.

PLAYER A

Lift the seed

Generate updrafts to control height, slow a fall, and navigate changing elevation.

PLAYER B

Shape its direction

Apply horizontal wind to steer, correct momentum, and guide the seed around obstacles.

SHARED GOAL

Reach the next shelter

Coordinate timing and force across an obstacle course. A failed attempt resets the current checkpoint.

02 / FIRST PLAYABLE LEVEL

Wind Corridor — a 90-second co-op challenge.

The first proposed multiplayer level is designed to teach interdependence without relying on text. Three readable encounters introduce the two inputs, require coordination, and end in a shared success moment. The existing local browser sandbox already tests dual-input movement, obstacles, collision and retry; the full Unity level below is the next production target.

BEAT 01 / UNDERSTAND

The first updraft

An open starting area lets Player A discover that lift changes altitude but does not advance the seed. Player B's horizontal wind immediately creates progress when combined with lift.

BEAT 02 / COORDINATE

The alternating gap

A high barrier followed by a low opening requires one player to control altitude while the other adjusts horizontal momentum. Collisions trigger clear audio/visual failure feedback and a retry.

BEAT 03 / ARRIVE

The shared shelter

Both players guide the seed to a visible destination ring. Its response confirms completion, and the game presents a shared replay state rather than separate individual scores.

DESIGNER PARAMETERS

What should be editable

Wind/lift acceleration, air drag, seed maximum velocity, obstacle positions, checkpoint response, camera damping and goal radius—configurable without rewriting the interaction system.

GAME-FEEL PARAMETERS

Make invisible force readable

HLSL cloud motion, wind-line particles, seed wobble, camera anticipation and audio intensity all derive from the same input/state data. Visual polish can be tuned independently of physics authority.

OBSERVABLE PLAYTEST

Is cooperation necessary?

Test whether either player can complete the route alone, where communication breaks down, how retries are interpreted, and which camera/framing parameters make the seed easier to follow.

04 / MULTIPLAYER IMPLEMENTATION SPECIFICATION

One authoritative simulation. Two complementary inputs.

The browser sandbox tests the shared-control mechanic. The Unity multiplayer version is designed around a host-authoritative seed with separate player input ownership, a synced checkpoint/goal state, and visual feedback derived from client-observed data.

PlayerInput / ownership

Each client owns only its input channel: Player A requests lift; Player B requests lateral wind. The server/host validates and combines those commands.

SeedMotor / physics

The authoritative Unity C# simulation applies gravity, combined wind acceleration, drag, collision and checkpoint rules at a fixed update rate.

NetworkSeed / replicated state

Position, velocity, level state and attempt/checkpoint events are synchronized. Clients interpolate render position; late input never directly overwrites authoritative physics state.

WindVFX / player feedback

Shader flow, cloud deformation, particles, sound and camera response read a normalized wind vector and seed state. Rendering quality can change without modifying the rules of the game.

DesignerConfig / content

ScriptableObjects or Inspector presets contain wind-force ranges, camera damping, obstacle layout and retry rules. These values support repeatable comparison across level variants.

Session / update workflow

Build version, host/client join and leave, disconnect state, level restarts and session errors are recorded for debugging. Playtest observations lead to a documented update cycle.

Implementation boundary: The local browser game is playable now. NetworkSeed, authoritative Unity session synchronization, two-client tests, designer Inspector tools and live deployment logs are the defined build targets, not completed features.

04 / POST-DEPLOYMENT DESIGN · LIVE OPERATIONS PLAN

A multiplayer build is only the beginning.

The planned operating cycle treats the prototype as a small online game that must be tested, updated and kept available for repeat sessions. These are implementation targets and acceptance criteria, not claims of prior commercial live-service ownership.

Build & release

Ship repeatable Windows builds with version identifiers, tracked release notes, a documented host/client setup, and rollback-ready artifacts.

Session monitoring

Record session join/leave, disconnect, desync symptoms, seed resets, checkpoint completion and errors in structured local or server-side logs.

Post-test fixes

Reproduce issues from two independent clients, isolate ownership or synchronization failures, fix them, and publish a patched build with concise change notes.

Designer-facing iteration

Adjust camera and wind presets independently of networking code, collect observed player behavior, and retune a level without recompiling gameplay rules when feasible.

Planned deliverables: Versioned builds · playable two-client demo · deployment instructions · recorded test session · issue log · at least one documented post-test patch. Operational evidence will be linked here after the tests are completed.
